# JD 自动定制与工作台

## 目的

把一个具体 JD 与候选人已有事实库连接成一份可审阅、可追溯的材料包。它调整证据选择、项目顺序、篇幅和语言；不改写事实，不捏造数字，也不自动投递。

## 私有缓存

`resume-evidence.json` 是案例内的派生缓存。建立或刷新时，Codex 从 `career-evidence-bank.md` 与较新的 `coaching-state.md` 读取事实，写入：

- 来源路径与 SHA-256；源材料变化后生成器必须拒绝继续使用旧缓存。
- 基础信息、工作与项目条目、稳定 ID、中英文保守表述、日期、工作性质、事实来源、方向标签和关键词。
- 已否定主张与待确认项。待确认项不能变成投递版事实。

缓存可以有 `anchor`、`family_priorities` 等选材元数据，但这些只影响排序，不能补充候选人的能力或成果。公开仓库只提交无个人资料的 schema 示例和合成测试数据；真实案例目录应单独忽略或保存在私有仓库。

本 Skill 附带的 `tests/fixtures/synthetic-case/` 是可运行的合成示例：它包含来源文件及与来源摘要一致的 `resume-evidence.json`。它只用于安装和回归测试，不能改名后直接当作真实候选人的档案。

## 路由与硬门槛

自动路由按岗位职责与标题判断，当前稳定方向是：

| 标签 | 用途 |
|---|---|
| `user-operations` | 用户、客户服务、客户运营与学习服务 |
| `ai-content-operations` | 知识库、文档结构化、内容质量与 AI 应用运营 |
| `implementation-support` | 项目协作、实施支持、问题跟进、指南与流程材料 |
| `product-operations` | 产品助理、产品运营、信息架构与用户路径 |

高级研究/工程、要求明确不相符的学历或长期经验，会阻断投递版；AE、销售型客户执行等职责不足的岗位保持“待确认”。不要把“AI”“客户”或“产品”这些单词本身当作匹配证明。

`jd_requirements.py` 仅评估明确且可识别的条件。它把结果分成：

- `supported`：已有事实源直接支持；
- `unknown`：资料没有足够证据，不能靠相邻经历补全；
- `not_met`：已记录事实与明确硬条件冲突。

规则不能理解所有自然语言。匹配报告中未列出的要求仍须由 Codex 和候选人阅读 JD 后复核。任何必需项为 `unknown` 或 `not_met` 时，包状态保持 `preparing`。

## 输出与验收

每次生成落在一个新的时间戳目录，包含 JD 快照、请求、选材记录、简历 Markdown/PDF、匹配报告、英文邮件草稿、面试追问和结果摘要。没有可信收件人时邮件草稿明确标为不发送。

输入栏中的公司与岗位名称是辅助信息而非必填项。仅贴 JD 时，生成器只会从 `公司：`、`Company:`、`岗位名称：`、`Job title:` 等明确标签提取元数据；否则写入“待确认”并添加外发前检查。它不会从模糊文案、公司介绍或相邻段落猜出公司或职位。

PDF 验收至少检查：一页、可提取文本、正常正文字号、无裁切/重叠、日期和工作性质一致、链接可打开。视觉检查必须看渲染图，不能只依赖文本提取。

本地页面只提供这些材料的生成和预览。邮件发送、官网填写、附件上传、点击提交、飞书写入和投递状态更新仍按各自的授权与回执规则执行。
