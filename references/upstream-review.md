# 持续改进的复核方法

触发：用户要求完善 Skill、报告实际失败或新接入一个工具时使用。此流程不创建定时任务，也不意味着对话结束后会自动检查 GitHub。

1. 先定位一个具体缺口和失败样本，判断是规则、数据脚本还是外部工具问题。
2. 阅读候选仓库的当前 README 和相关 SKILL/脚本；记录日期、来源路径、分支或确实取得的 commit。没有 commit 就写未固定，不能编造。
3. 分别记“文档声称”“已读代码”“本地验证”“外部实测”，不要用星数、宣传截图或有 tests 文件夹代替验证。
4. 对照现有模块：已有功能不再堆一套；可吸收的规则独立改写；涉及代码复用时确认许可、兼容性和维护成本。
5. 每次选择一个能独立验收的改动。规则用真实任务或桌面推演，脚本用失败回归和现有必要检查；不为通用工作流强制所有用户额外审批。
6. 更新研究记录与能力矩阵；同步安装版前确认源文件一致。保留原案例和原材料，不迁移个人数据到共享 Skill。

优先观察的项目与本地对照：

- ASu-skills：项目证据复盘 → 本地证据库与故事库。
- One-Stop-Resume-Copilot：修改对照与排版 → review-draft 模板、现有文档 Skill。
- job-application-copilot：附件/网站字段管理 → 本地事件与 execution-readiness。
- job-autopilot：恢复入口与运行状态 → checkpoint；其校招职位库不能默认适合当前用户。
- get-offers：邮件草稿与投递包 → email/manifest；是否新增 EML 取决于实际邮件工作流。
- ApplyBuddy：硬条件与偏好分开 → 岗位匹配，不把偏好全当硬排除。

研究记录保存在项目 `skill-reviews/`，不把长篇比较、私人案例和未采用的设计塞进入口文件。
